# 设计取舍与已知限制

命令与选项见 [reference.md](reference.md)，概览见 [README](../README.md)。

## 核心原则：fail-closed

指定了窗口，就必须**验证通过**才动手。选择器歧义、窗口不合格、抢不到前台——
统统拒绝执行并返回对应退出码，**绝不"猜一个窗口往里敲"**。

保证落在退出码上：

| 码 | 保证 |
| --- | --- |
| 3 / 4 | 失败发生在解析或资格检查阶段，**注入之前** |
| 5 | 焦点回读验证失败，**注入之前** |
| 1 | 可能已经发了一部分（例如 `SendInput` 被 UIPI 拦截）——所以脚本重试**只重试 3/4/5** |

这条"3/4/5 必然一个字节都没发"的不变量，是 `--retry` 安全性的全部依据：
重试**绝不可能重复一个"做了一半"的动作**。

## 目标窗口怎么选

匹配之后按三层收敛，每一层只在前一层"还剩东西"时才生效：

1. **优先可见窗口** —— 一个应用除了主窗口还有一堆隐藏辅助窗口（IME、WorkerW、托盘幽灵），
   `--process QQ` 这种查询会全匹配上。全都不可见时才回退去看隐藏的。
2. **优先无主窗口** —— 有 owner 的窗口是次要窗口（对话框、弹层、IME 桥、WinUI 的
   `PopupWindowSiteBridge`）。实测过：点一下记事本，它就多出一个"可见、可用"的弹层，
   让 `--process notepad` 直接变成歧义。
3. **过闸门** —— 剩下的一起做客观判定（见下），全部不合格就报错。

仍然多于一个可用窗口 → 报错并要求 `--pick`，**不自动挑**。

## 闸门查什么（全部是客观判定）

| 检查 | 结论 |
| --- | --- |
| `IsWindowVisible` | 隐藏窗口拒绝（强行显示隐藏窗口可能只得到一帧静止画面） |
| `IsIconic` | 最小化拒绝，除非显式 `--allow-restore` |
| `DwmGetWindowAttribute(DWMWA_CLOAKED)` | 挂起的 UWP / 其他虚拟桌面的窗口拒绝 |
| `SendMessageTimeout(WM_NULL)` | 消息队列不响应（500ms）拒绝 |
| `IsWindowEnabled` | 被禁用（`WS_DISABLED`）拒绝——它**设计上就忽略输入**，典型是模态对话框禁用了宿主窗口 |

## 可靠性细节

- **真事件**：`SendInput`，不是 `SetCursorPos`。光标移动走
  `MOUSEEVENTF_MOVE | MOUSEEVENTF_ABSOLUTE | MOUSEEVENTF_VIRTUALDESK`，多显示器按虚拟桌面算。
- **坐标精度**：绝对坐标会被量化到 0..65535，移动后**回读校验**、最多重试 3 次，
  实在不行才退到 `SetCursorPos` 兜底。
- **打字可靠性**：字符间隔默认 15ms，结尾再留 60ms 排空队列。实测过 WinUI 记事本
  "连灌 24 字符丢尾字"的偶发竞态，加缓冲后连续多轮剪贴板往返校验逐字符一致。
- **DPI 感知**：`app.manifest` 声明 Per-Monitor V2。缺了它，缩放非 100% 的显示器上
  系统会虚拟化坐标，`ClientToScreen` 算出来的点会整体偏移。
- **单次执行**：进程起来 → 注入 → 打印结果 → 退出，没有常驻进程和后台线程。
  等待与轮询只出现在脚本的 `waitfor` / `waitgone` 里，且是显式的、有硬超时的。

## 为什么不做"这个窗口是不是只剩一帧"的启发式检测

起因是一个真实案例：某个 Electron 应用把窗口缩进托盘后，`ShowWindow` 能把它"拉"出来，
但拉出来的只是**上一帧画面**（渲染子窗口已经没了），点它、打字全都没反应。
**能不能自动识别这种窗口？** 调研后决定：**不做**，而且这个决定有数据。

在本机 16 个可见窗口上实测（2026-10-02）：

| 候选信号 | 实测结果 |
| --- | --- |
| "Chromium 类名但找不到渲染子窗口 = 空壳" | **3 个 Chromium 窗口里 2 个踩中，其中包括当时活得好好的 DSH 窗口 → 对活窗口的误报率 100%**，直接否决 |
| `GetGUIThreadInfo` 的 caret | 16 个窗口全都没有 caret（它本来就是一瞬一瞬的），抓不到 |
| `IsWindowEnabled` / `WS_DISABLED` | 全部 enabled —— 信号真实但罕见，**已加入闸门** |
| UIA `WindowInteractionState`（`NotResponding` / `BlockedByModalWindow`） | 理论上最对症，但需要 COM 互操作或额外依赖，而且**手上没有已知的"壳窗口"能验证它** |

结论：**与其用没验证过的启发式去猜，不如让脚本自己声明期望**。
`waitfor` / `waitgone` 加上分级退出码，把"动作到底有没有生效"变成**可断言的确定事实**。

万一以后遇到"输入发出去了但什么都没发生"，排查顺序建议是：
`window inspect` 看闸门怎么说 → 用 `waitfor` 表达期望的结果 →
实在需要像素级证据时，`PrintWindow` 前后比对（`--verify-change`）仍是备选，
但它**只能当报告用**：点活窗口的空白处画面同样不会变，假阴性无法避免。

## 已知限制

- 目标窗口若以管理员权限运行，普通权限的 KeyMouse 会被 UIPI 拦下（退出码 1，程序会提示
  "run KeyMouse elevated too"），用管理员权限跑即可。
- UAC 安全桌面（"是否允许此应用更改"弹窗）、Ctrl+Alt+Del 无法模拟，系统设计如此。
- **遮挡检测做不到**：窗口被别的窗口盖住一半没有可靠 API 可查；`--strict-point`
  只能校验"某个点下面的窗口是不是目标"。
- 验证通过到实际注入之间有毫秒级 TOCTOU 窗口，理论上仍可能被抢焦点。
- **客户区坐标包含"窗口装饰"**：现代应用（WinUI/Electron）的客户区里有标签栏、工具栏。
  实测记事本客户区 y≈80 是工具栏，点那里之后**应用会吞掉你接着输入的第一个词**
  （`hello from…` 变成 `from…`，`A B C…` 变成 `B C…`）——这是应用自身行为，真人这么点也一样。
  用 `-wx/-wy` 时瞄准内容区（记事本 y≥160 就没问题），不确定就先 `window inspect` 或截图确认落点。
- **选区浮层**在打开时取一次窗口列表：浮层开着时**新弹出**的窗口悬停不到（拖动框选不受影响，它只记坐标）。
- **不会从正在操作电脑的人手里抢焦点**：温和尝试 3 次失败就退出（退出码 5），一个字节都不发。
- **`probe` 读的是像素，不是控件的文本**：默认的 `--capture screen` 会被遮挡影响（盖住的窗口会被读成前景内容）；
  最小化窗口在取像之前就被闸门拒掉（退出码 `4`），`--capture print` 也不改变这一点；
  壳窗口（WebView / Electron 的 `*-siw` / `*-sic`）可能报 `0×0` 客户区，此时任何区域都判越界（退出码 `2`）。

## 测试策略

两层，刻意分开：

| 层 | 内容 | 需要桌面 | 在 CI 里 |
| --- | --- | --- | --- |
| 单元测试 | 脚本分词器、argv/选项解析、按键名映射、选择器匹配、候选筛选、状态串、重试策略、变量替换、wait 解析、循环结构与展开计数、目标继承、**单进程派发（注入 dispatcher 数调用次数）** | ❌ | ✅ |
| 桌面冒烟 | 启动自己的靶子窗口（`tests/KeyMouse.SmokeTarget`）走完整链路：退出码矩阵、打字往返比对、相对拖拽选中的文本、变量、重试与报告、等待、禁用窗口、`--dry-run` 零输入、`vk:` 逃生口、stdin、`--keep-going`、目标继承、**循环真的写对了几行**、**运行期间恒为 1 个进程** | ✅ | ❌（CI 没有交互式桌面） |

**只有两层都断言过的行为才算被锁住**：单元测试证明逻辑，冒烟测试证明它真的作用到了桌面上。
"脚本在单进程内执行"就是这么钉的——如果哪天有人改成"每行起一个进程"，单元测试里那个
dispatcher 根本不会被调到。

单元测试**故意不用任何测试框架**：一个普通控制台程序，零依赖、离线可跑，
`dotnet run` 就能执行，非零退出码即失败。

它已经证明过价值：上线后第一次运行就发现 `vk:0x5B` 这个从 v1.0 就写在文档里、
**却从来没工作过**的逃生口（`ushort.TryParse` 读不了 `0x` 前缀）。

## 脚本为什么长这样（v2）

### 一、一个脚本自始至终只用一个进程

`run` 把每一行交给同一个进程内的派发逻辑，**不重新启动自己**。这不是省事，而是三件事的地基：

- `window focus` 的目标可以被后面的命令继承——状态在内存里，不需要磁盘上放一个"当前目标"；
- 循环变量、`${变量}` 在展开时就地生效；
- 没有"每条命令付一次进程启动开销"的税。

代价是它**不能跨进程**：在 shell 里敲两条独立命令，第二条没有任何"上一条"可继承。这是刻意接受的。

### 二、目标继承只在脚本内，命令行永远自带目标

跨进程继承只有两条路：环境变量或暂存文件。两者都是**看不见的状态**，而这个工具最该躲的失败模式
恰恰是"输入落到了你以为不是它的窗口"。昨天 focus 的记事本，今天的 `key type "密码"` 还往那儿发——
这种事故不值得用"少打几个字"去换。

脚本内则相反：继承发生在**一次可读、可审、可重放的文本**里，一眼能看完，继承的行在日志里还会标出来
（`← 继承目标 --title "记事本"`）。

### 三、循环必须有界，而且结构先于执行被检查

- 单层次数上限 1e6、**展开后总命令数上限 1e5**：跑飞的脚本在动手之前就被拒绝，而不是跑到天亮；
- 不提供无限循环，也不提供 `break`——要"等到条件成立"是 `waitfor` 的活；
- `repeat`/`end` 不配对、次数非法、`end` 带参数、影子变量、变量用在了循环外、未定义的 `${...}`：
  **全部在第一条命令执行前**带行号报错。

最后一条是刻意保住的不变量：**脚本要么从头跑到尾，要么在动手之前就被拒绝**，
不会出现"跑到第 40 行才发现第 3 行写错了"。

### 四、嵌套必须给循环变量命名

两个未命名的循环都绑定 `${i}`，内层会静默盖住外层——写的时候看着没问题，读日志时才发现外层索引
根本取不到。与其事后解释，不如直接拒绝并告诉你写成 `repeat 3 as row`。

### 五、为什么还没有条件分支

`waitfor` / `waitgone` 已经覆盖了最常见的"等某个状态成立"，而条件分支会把这个"一行一条命令、
逐行可读"的模型变成一门小语言。真要更复杂的控制流，用调用方自己的语言（PowerShell / 批处理）
拼接更诚实。

**现在能读回值了**（`probe` 把区域读成文字），但"有操作数"不等于"该写 `if`"——判定谓词与控制流的
顺序见下文「感知与控制流」。

## 感知与控制流（识图 / OCR）

> **状态：感知出口 `probe` 已落地（2026-10-03），判定谓词与 `if/while` 仍未实现。**
> 这一节刻意先于代码存在——上文 `--verify-change` 的教训就是"边界不定死，实现时一定会走偏"；
> 事实也证明这有用：实现把下面几条逐条检验，被推翻的都记着（取像方式、置信度地板、光标）。

### 要解决的问题

脚本需要"画面里出现某段文字 → 改变执行流程"。这不是加一个命令，而是**三件必须分开造的能力**：

| 层 | 职责 | 今天有什么 |
| --- | --- | --- |
| 感知 | 把像素变成**可比较的值** | **`probe`（2026-10-03 落地）**：区域 → 文本 + 逐词置信度 + 引擎身份，N 次逐字一致才算看清 |
| 判定 | 把读数变成真 / 假 | 只有闸门（窗口在不在、能不能用）；**文本谓词还没有** |
| 控制流 | 按真假改变路线 | 只有 `repeat <n>` |

**顺序不能倒。** 先做 `if` 会得到"没有操作数的运算符"——判定需要一个可读回的值。
这个值现在有了（`probe --json`），所以下一步是给读取加**客观谓词**（`--contains` 之类），
再下一步才是 `if/else` + `while`。

### 三条硬边界

1. **感知只报告，不判断。** 引擎的输出永远是"我看到了什么"，判断权在脚本/宿主。**工具绝不猜。**
2. **判定只有客观谓词。** 位置证据、容错匹配、多次一致性、窗口属性、区域像素变化。**永不引入表达式求值器。**
3. **控制流只到 `if/else` + `while`。** 不引入函数、递归、数据结构；更复杂的控制流请换宿主语言驱动，而不是给文本格式打补丁。

> **判据**：一个新特性如果要求"实现一个求值器"，它就不该进这个项目。

### 实测事实（Windows 11 本机，2026-10-03）

下表是探路 **Windows OCR 路线**时测的（那条路最终没被采用，见下文「引擎决策」）；
其中"区域化""不要求逐字相等""读到空不是失败"这几条结论，对所有引擎都成立。

| 事实 | 数据 | 对设计的影响 |
| --- | --- | --- |
| Windows 自带 OCR 能否零依赖用 | **能**：TFM 指到 `net10.0-windows10.0.19041.0`，WinRT 投影由 .NET SDK 提供，**0 NuGet 0 警告** | OCR 不必成为第三方依赖；但代价是最低系统版本抬到 Win10 2004 |
| 可用语言 | WinRT 查询（2026-10-03 复核）：本机可用集合就是 **`en-US`、`zh-Hans-CN`**，`ja` 不在其中。早先记的"只有 `zh-Hans-CN`、`en-US` 不可用"**是错的** | **语言集是机器相关的**：必须先报告能力，没有对应引擎就明确失败，绝不静默降级 |
| 全屏 OCR 成本 | 5120×1532：解码 76 ms + **识别 ~700 ms**，99 行 | 成本与**区域成正比**——感知的单位必须是区域（按钮大小的区域约 10 ms 量级） |
| 同图重复性 | 连读 5 次**逐字相同 5/5** | 引擎是确定的：**"同一输入同一输出"是免费拿到的** |
| 像素扰动稳定性 | 右移 1px：字符二元组相似度 **91.7%**；下移 1px：**93.5%** | 位移一个像素就有 **~8% 的字符漂移** → 判定**绝不能要求逐字相等**；感知区域必须用**客户区相对坐标**（区域指纹还没实现） |
| 空白区域 | **0 行 / 0 ms / 不报错** | "读到空" ≠ "读失败"：判定层必须能区分二者 |
| 置信度 | **没有**：`OcrWord` 只有 `BoundingRect`+`Text`，`OcrLine` 只有 `Text`+`Words` | **"置信度阈值"这条路在系统引擎上不存在** → 可信度只能靠下面的共识判定与引擎可替换来拿 |
| 中文切分 | 每个汉字是一个 `word`，行内带空格 | 匹配前必须**规范化空白** |

### 感知出口：`probe`（已实现）

一次真实读取的输出（记事本 600×80 的标题栏区域，`--reads 2`，退出码 `0`）——**实现就是这个形状**：

```jsonc
{
  "ok": true,
  "engine": { "kind": "external", "command": "C:\\Program Files\\Tesseract-OCR\\tesseract.exe",
              "version": "tesseract v5.5.3.20260724", "languages": "eng+chi_sim",
              "tessdata": "…\\KeyMouse\\tessdata",
              "models": [ { "name": "chi_sim", "bytes": 2469156 }, { "name": "eng", "bytes": 4113088 } ] },
  "window": { "handle": "0x1D097E", "title": "新建 文本文档.txt - Notepad", "pid": 31612 },
  "geometry": { "extendedFrame": [-2571, 81, 2582, 1390], "visibleFrame": [-2562, 81, 2564, 1381], "inset": 9 },
  "region": { "space": "client", "rect": [0, 0, 600, 80] },
  "reads": 2, "consistent": true,           // 不是 true 就别拿它做判断
  "confidence": 76.9, "minConfidence": 30,  // 地板只用来抓"彻底没读出来"
  "elapsedMs": 689, "note": null,
  "lines": [ { "text": "下 新 建文 本 文档 txt x | +", "rect": [16, 16, 135, 240],
               "words": [ { "text": "新", "conf": 97, "rect": [271, 100, 81, 51] } ] } ]
}
```

字段与全部选项见 [reference.md](reference.md)。两处**设计里有、实现里没有**：区域指纹
（`region.fingerprint`）与模型哈希（`models[].sha256`）——前者等"缓存 / 位置证据"出现真实需求再加，
后者等换模型成为实际痛点再加；**没有的东西不写进输出**。

| 退出码 | 含义 |
| --- | --- |
| `0` | 读到了，且 N 次读**逐字一致**；`lines` 为空表示这块区域确实没有文字 |
| `2` | 参数或区域错误（越界、缺选择器）——**不猜也不截断** |
| `3` / `4` | 沿用现有窗口语义（选择器无匹配 / 目标不可用，含最小化） |
| `6` | **没看清**：N 次不一致 / 置信度低于地板 / 没有可用的引擎 / 取像失败 |

还有一道**取像之前的闸门**：最小化窗口在选 `--capture` 之前就被拒（退出码 `4`），
所以 `--capture print` 并不能读最小化窗口——"让窗口自己画"和"系统已经停止绘制"是两件事。

`6` 与 `3/4/5` 同一哲学：**"没看清"必须是失败，不是猜测**；它同样属于"确定没发出输入"，因此**可以安全重试**。

> **实现后才被实测推翻的三处（2026-10-03）**：
> 1. **取像默认改用屏幕抓取，不是 PrintWindow。** 设计里写的是 PrintWindow（不画光标、可读后台窗口），
>    但它的几何在本机对不齐：图的原点既不等于 `GetWindowRect`，也不等于 DWM 的可见边框矩形，
>    实测抓到的文字被切掉上半截。而屏幕抓取那条路在语料测量里**读对了每一个样本**，
>    所以默认按证据选 `screen`，PrintWindow 保留为 `--capture print`。
> 2. **置信度地板从 60 降到 30。** 60 是在合成图上标定的（读对时 92~96）。
>    真实屏幕文字受 ClearType 影响：一次**读对**的 `ProbeCheck12345` 只有 55.8，
>    而此前的垃圾读数有 51.6——**两者分布重叠**，所以地板只能用来抓"彻底没读出来"（实测 14.7 / 21.4）。
> 3. **屏幕抓取会把光标一起抓进来，而光标会闪。** 两次读取因此差一个 `|`，共识判定误杀了正确的读取。
>    处理办法是：光标字符**只从比较里剔除，绝不从输出里剔除**。
> 4. **`--space window` 在屏幕取像下偏移了一整条边框。** 建选区浮层时才撞出来：默认的 `--capture screen`
>    把区域加到**客户区原点**上而不是窗口矩形原点，于是选标题栏读到的其实是客户区顶部——
>    证据是同一块区域在 `client` 与 `window` 两个坐标系下产出的图**逐字节相同**（sha256 都是 `3EAB5A65…`）。
>    修好之后标题栏第一次读对了（冒烟靶子标题读成 `a@ KeyMouse 冒 烟 靶子`，conf 76，三次读取逐字一致）。
>    回归测试进了 smoke：同一批屏幕像素从两个坐标系走，必须逐字节相同。
> 5. **取样与预处理：先选错了默认，再按数据把"要不要预处理"也改了。**
>    ① 用户报小区域放大后有肉眼可见的"重影"，第一版测量得出"3× 最近邻 9/10、双线性 6/10"，
>    据此把默认取样改成最近邻——**那次测量是错的**：光标当时在区域内，而光标会让整行读崩（见第 6 条）。
>    把光标挪出区域后重跑，取样方式之间的差别消失。
>    ② 用户随后要求"**原始像素直送引擎**"，于是 `--scale` / `--pad` / `--normalize` 全部改成选项，
>    默认不做任何变换。20 个真实样本复测（留档 `tests/evidence/20261003-171722/`）给出的代价是：
>    **原始像素 12/20、原始+归一化 12/20、3× 最近邻 11/20、3× 双线性 9/20、3× 双线性+归一化 15/20**
>    （平均 conf 89~92；只有原始默认那组出现过 3 次退出码 6）。
>    结论：**放大 + 归一化确实更准**（15/20 vs 12/20），但默认仍是"原图直送"——这是使用者的选择，
>    工具负责把选择权和数据一起摆出来；想要那 15/20 就是一条命令：`--scale 3 --pad 16 --normalize`。
> 6. **"把光标从比较里剔除"不够——光标会让整行读崩。** 第 3 条只把它当成"多出一个 `|`"的噪声，
>    实际测量：同一块区域，`你好，世界` 读对（conf 84.7），**加上光标**读成 `Re,Hh`（conf 49.8）；
>    光标闪烁还让两次采集互相不一致 → 退出码 `6`。两个帧的截图、JSON 与复现命令都留档在 `tests/evidence/`。
>    连带一条：**区域高度要盖住整行**，`0,0,400,20` 切掉字底读成 `4eim+s`，`0,0,400,32` 正常。

### 手动选区：`region pick` / `probe --pick-region`（已实现）

**为什么要有它**：`probe` 拒绝猜区域，而凭记忆报坐标实测猜了三次、三次落在壁纸或空白上。
把"看着屏幕指一下"交给鼠标，比让人报四个数字可靠。它只做一件事：**把人类画的屏幕矩形翻译成
`probe` 认得的坐标系**——不读任何文字。

| 决定 | 理由 |
| --- | --- |
| 打开前抓一张**冻结快照**当背景 | 瞄准的东西不能动；浮层自己也不会被抓进图里 |
| 显式 `SetWindowPos(HWND_TOPMOST)` | 实测只设 `TopMost` 时浮层仍在目标窗口**下面**，拖动落到了目标窗口上 |
| 取消键注册为**全局热键** | 后台进程抢不到前台；只在有焦点时才灵的 `ESC` 不算取消键 |
| 线程 DPI 强制 Per-Monitor V2 并**开浮层前断言** | WinForms 会把 UI 线程降成 SystemAware：量到的桌面是 2560×1440、真实 5120×1532，坐标会被整体缩放。断言不过就退出码 `4`，宁可不给坐标 |
| 窗口列表只在开浮层时取一次 | 每次鼠标移动都枚举约 400 个顶层窗口，成本和它要帮的 OCR 差不多 |
| 坐标系自动判定：客户区 → 窗口矩形 → 无 | `probe` 只认前两种；第三种只报屏幕坐标 + 原因，不给可粘贴的命令 |

**代价（实测，2026-10-03）**：浮层用 WinForms，发布体积 **自包含 36 MB → 49 MB**（压缩后；
未压缩 70 MB → 111 MB），fx 单文件 295 KB → 318 KB。不用选区的命令一行都没变重。
若哪天这个体积不能接受，替代方案是自绘 Win32 浮层（约 250 行，体积不变）——届时删掉本节这张表的第二行即可。

**测法**：`region pick --rect`（非交互）覆盖坐标系判定；smoke 用 KeyMouse 自己的鼠标与键盘驱动浮层，
覆盖拖动 / 单击 / `ESC` 三条路径，并用"两个坐标系必须给出同一批像素"钉住上文推翻 4 的那个 bug。

### 共识判定：把"可信度"落成机制

用户要的"识别要可信、要一致"，不能靠期望引擎稳定，必须靠三条机制：

1. **共识判定（consensus）**：同一区域连续读 N 次（默认 `--reads 2`），**全部逐字相同才算看清**；不一致 → 退出码 `6`。
   实测支撑：同图 5/5 逐字相同 → 这个判据既有效又便宜。真正的成本在引擎：Tesseract 路径 600×80 读两次共 689 ms，
   Windows OCR 那条路区域级只要 ~10 ms——差的是引擎，不是判据。
2. **引擎身份进输出**：`kind` / `command` / `version` / `languages` / `tessdata` + 模型名与字节数
   （模型哈希只在下载时记录，还没有进输出——理由见上文）。
   换引擎或换模型时，**一致性的断点可见**——这是"可复现"的工程表达。
3. **规范化 + 容错匹配**：匹配前规范化空白；容错程度由**脚本声明**（相似度下限 / 允许的编辑距离）。
   1px 就有 8% 漂移，所以"要它一字不差"本身就是一个错误的要求；但**要多严，必须写出来**。

### 引擎决策与实测（2026-10-03）

**决定：默认引擎用 Tesseract**（使用者的选择；未做引擎间横向比对，下表是 Tesseract 的单侧实测）。

| 项 | 实测结果 |
| --- | --- |
| 引擎 | Tesseract **5.5.3**，`C:\Program Files\Tesseract-OCR\tesseract.exe` |
| 语言数据 | 用户级目录 `%LOCALAPPDATA%\KeyMouse\tessdata`：`eng` 4,113,088 B、`chi_sim` 2,469,156 B（**fast** 模型；下载时记过 SHA256，`probe` 输出里目前只有名称与字节数） |
| `configs/` | **必须存在**（26 个文件，`tsv` 在内）——缺了它就拿不到置信度 |
| 调用方式 | `tesseract <图> <输出基> -l chi_sim --psm 6 --tessdata-dir <目录> tsv`（`--psm` 早期测量用 7，实现固定为 6）；`--tessdata-dir` 与 `TESSDATA_PREFIX` 都可用（后者指向 tessdata 本身或它的父目录均可） |
| **置信度** | **可得**，但作用边界与直觉相反——见下节实测 |
| 识别质量（fast 模型，合成样本） | 12pt 中英混排**完全正确**；16pt 纯中文短词**完全错误**（`另存为` → `ABH`） |
| 标准模型 | 已补：`chi_sim` **44,366,093 B**、`eng` 23,466,654 B，装在 `%LOCALAPPDATA%\KeyMouse\tessdata-std`（fast 那套保留在 `tessdata`，**两套并存可切换**）。经 `gh-proxy.com` 取得（GitHub 直连超时、jsDelivr 对 >20 MB 文件返回 403） |
| 每个模型目录都要 `configs/` | 新建模型目录时**必须**一并复制 `configs/`（26 个文件）——否则 `tsv` 拿不到、输出为空，而错误信息会被 `2>$null` 吞掉。这条我犯了两次 |

### 真实语料与默认参数（实测）

**合成渲染会系统性低估引擎能力**，所以第二批语料是**真实窗口**：用 KeyMouse 自己往靶子窗口打字，
**打进去什么字就是标准答案**；取词区域的坐标也从 `mouse move -wx` 的回报里算出偏移，
不靠记忆猜（此前三次凭记忆挑区域，三次都落在壁纸或空白上）。

7 个样本 × 2 套模型 × {原始, 3× 放大 + 16px 白边}：

| 配置 | 逐字正确 | 平均耗时 |
| --- | --- | --- |
| **fast + 3× 预处理** | **5/7** | **290 ms** |
| fast 原始 | 4/7 | 279 ms |
| **standard 原始** | **5/7** | 710 ms |
| standard + 3× 预处理 | 4/7 | 725 ms |

四条结论：

1. **模型默认用 fast**：正确率与 standard 打平（5/7），但**快 2.5 倍**；
   standard 只在一个场景明显更好——**长中文句子**（`请输入文件名后点击保存按钮`：
   fast 原始 conf 21 彻底失败，standard conf 95 正确）→ 定位为**难例回退**，不是默认。
   （上表里的"3× 预处理"当年是默认，**现在不是了**：默认把抓到的原始像素直接交给引擎，
   放大与归一化都改成选项——见下文推翻 5。）
2. **置信度的真实边界（推翻上一版用合成样本得出的"≥90 阈值"）**：
   - `conf < 60` 在 28 次读取里出现 **3 次，三次都是彻底失败**（`FRA` / `RHAREFSZERSHRERA` /
     `kevMouseSVRERZ`）→ **`conf ≥ 60` 可以当"到底读出来了没有"的地板**，低于它就是退出码 `6`；
   - 但**只错一个字也常常有 83~96 的 conf** → **逐字正确不能靠阈值保证**，判定层必须做
     **容错匹配**（脚本声明允许几个字不同），而不是把阈值抬高。
3. **光标会被读成 `|`**：打完字立刻截图，文本光标进了画面（本批 6/7 个样本末尾都多出一个 `|`）。
   原设计打算用 `PrintWindow`（不画光标）绕开，但它的几何本机对不齐（见上文推翻 1），这条路被弃用。
   现在的做法是：共识判定会因此误杀（实测两次读差的正是这一个 `|`），所以光标字符
   **只从比较里剔除，绝不从输出里剔除**。
4. ~~**标题栏不能当基准样本**~~：**这条作废**。当时四组配置都没逐字读对（conf 52~91），
   但那正是上文推翻 4 的原点错位造成的——量到的根本不是标题栏。修好之后重测：`KeyMouse 冒烟靶子`
   读成 `a@ KeyMouse 冒 烟 靶子`（conf 76，三次逐字一致），前缀 `a@` 是窗口图标被当成了文字。
   **标题栏能用，只要别把图标算进"逐字相等"里。**

由此确定三条工程约定：

1. **引擎与模型身份必须进输出**（实现里是 `kind` / `command` / `version` / `languages` / `tessdata`
   加模型名与字节数）。换模型只是换一个文件——输出里不记引擎，事后就无法解释"为什么昨天读得出、今天读不出"。
2. **置信度是第一等证据，但它只回答"到底读出来了没有"**：地板默认 30，低于它判 `6`。
   实测读对 55.8~96、读错 14.7~52，**两种分布重叠**——所以精确性由脚本声明容错匹配来管，
   不能靠抬阈值。系统 OCR 那条路连这个数字都没有，这是换 Tesseract 的直接收益。
3. **不做"随便圈一块试试"的用法**：本次实测里三次凭记忆挑屏幕区域，全部落在空白或壁纸上，
   OCR **正确地返回了空**——**"读到空"不等于"读失败"**。区域必须由脚本明确给出
   （客户区相对坐标；区域指纹待出现缓存需求时再加），工具不猜。

**备选引擎**：Windows OCR 仍然可用（零依赖、离线；WinRT 查询本机可用语言为 `en-US`、`zh-Hans-CN`），
适合"不要任何外部依赖"的场景；短板是**没有置信度**、语言集取决于系统装了什么。
**这条路目前只有探路数据，没有实现**——要用得按同一套尺子重新测一遍。
**可插拔**：`--engine <外部命令>` 的实现是**按 Tesseract 的命令行调用**
（`<引擎> <图> <输出基> -l <语言> --psm 6 [--tessdata-dir <目录>] tsv`，读它产出的 tsv），
别家引擎必须兼容这套参数才能直接用；实测只跑过 Tesseract 一家，JSON 里 `kind` 对任何外部命令都写 `external`。
**不打包模型**：语言数据由使用者自备（本次做法即范例：用户级目录 + 官方 fast 模型 + 记录字节数）。

### 选型用同一把尺子

**不拿引擎宣传的准确率选型。** 用同一批真实截图跑四组指标，横向比较：

1. 重复性：同图连读 N 次是否逐字相同；
2. 扰动稳定性：±1px 平移、缩放 0.9、JPEG 压缩后的相似度；
3. 跨语言：中英混排、艺术字体、小字号的识别率；
4. 成本：区域级单次耗时。

Windows OCR 的基线已经测出（同图重复 5/5、±1px 相似度 91.7% / 93.5%、全屏 ~700 ms / 99 行），
换引擎时用同一套尺子才有可比数据。

### 两条路线，同一套接口

| 路线 | 做法 | 代价 / 收益 |
| --- | --- | --- |
| **甲：宿主驱动**（先做） | KeyMouse 只提供 `probe --json`，条件与循环写在宿主（PowerShell / C#）里 | 每次调用 ~58 ms，但在 ~700 ms 的 OCR 面前只占 ~9%；宿主有调试器、测试与库 |
| **乙：进程内** | 把判定与 `if` / `while` 下沉进脚本语法 | 换回单进程、`--report` / `--retry` / `--dry-run`、"一个脚本文件跑完"的体验 |

**先甲后乙**：甲的验证期用来定死 `probe` 的 JSON 形状；接口定死后，感知放哪一边都只是搬运。

### 明确不做

- **不做表达式求值器、函数、递归、数据结构**（见硬边界 2、3）。
- **不回 UIA 读控件文本那条路**：Chromium / Electron 大量控件读不到（实测 16/16 空），这条已经被论证过。
- **不让 `waitfor` 长出一个 `--text`**：那等于把概率塞进确定性判定，破坏"3/4/5 必然一个字节都没发"的语义。
- **不内置模型与语言包**（形态优势比"开箱即用"更值钱）。

## 路线图

暂无排期。记录在案的候选项：

- `--verify-change`：`PrintWindow(PW_RENDERFULLCONTENT)` 前后像素比对，**只能当报告用**（见上文）。
- `record`：把一次手动操作录成脚本；产物必须是**窗口相对坐标**形式才可重放。
- 跨进程继承：只在有真实需求时做，且必须**显式**（环境变量或 `--inherit` 开关），不能是隐式的。
- JSON 脚本输入：给"由程序生成脚本"的场景（转义规则明确、每种语言都有解析器）；
  人写的脚本继续用文本格式。
- **感知与控制流**（识图 / OCR）：设计见上文「感知与控制流」一节；`probe`（感知出口）与
  **手动选区**（`region pick` / `probe --pick-region`）**已落地（2026-10-03）**，
  下一步是**判定谓词**（`--contains` / `--matches` + 显式容错预算），再下一步才是 `if/while`；
  两条路线（宿主驱动 / 进程内）共用同一套接口。
- 条件分支 / 跨行断言：只有在"可读回的值"存在之后才有意义——**这个值现在有了**（`probe --json`），
  所以下一步是给读取加谓词，而不是先写 `if`。

已实现（曾列在这里）：**循环** `repeat n [as 名字] … end`、**脚本内目标继承**。
