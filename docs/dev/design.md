# 引擎设计：从流程到桌面动作

读一条流程时，区分**用户意图**、**计划中的步骤**和**桌面实际效果**。文件能加载不代表窗口可用，系统调用成功也不代表应用完成了业务操作。这三个层次分别由格式校验、目标检查和观察结果验证。

1. [流程契约](../../src/KeyMouse.Core.Flow.Validation/flow.schema.json)给出字段、类型与范围。加载器在发送输入前拒绝非法格式，编辑器从同一契约生成检查器。
2. `FlowPlan` 将嵌套块、循环、变量和子流程编成语句树。`FlowRunner` 逐次判断分支，区分步骤在文档中的位置和本次执行编号。
3. JSON 输入叶子交给类型化执行器；文本脚本仍走命令行解析。两条路径复用底层窗口、安全检查与输入实现。报告保留失败位置与退出码，调用者据此决定是否重试。

**计时。** 关键录制保留意图，不复刻空等；完全录制保留实际节奏。新步骤把间隔写入 `delayMs`，只在执行该步骤前等待。拖动和长按自身的用时不再计入下一步的间隔。旧 `atMs` 保持兼容。

**目标。** 屏幕坐标、客户区鼠标消息和有语义的后台控件是三种不同能力。无法唯一确定窗口或不满足权限条件时，终止动作，不回退到当前前台。对具体应用的支持以[靶窗实测](background-input-feasibility.md)为界。

**证据。** 带截图的报告便于区分取点错误与识别错误，也可能包含业务画面。截图留在本机，公开回归用合成数据。另见[执行架构决策](adr/0002-execution-abstraction.md)、[系统调用失败处理](native-failure-policy.md)。
